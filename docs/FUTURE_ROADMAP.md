# 未来功能：多成员订阅、微信接收与多信息源

规划日期：2026-10-22。最初为未来功能可行性与待办；操作者随后明确授权按计划实现独立订阅并部署，阶段6主体已上线，原配置迁移给唯一成员MaTianye（实际UserID `MaTianYe`）。实施说明见[INDEPENDENT_SUBSCRIPTIONS.md](INDEPENDENT_SUBSCRIPTIONS.md)，实际测试与生产边界见PROGRESS.md。下文“当前基础”描述实施前基线。其他微信渠道和新增真实来源仍按各自依赖推进。原生产三只股票及关注配置保持不变，只继承新服务已有去重和基线，不导入旧系统seen，不安排系统升级。自动监控保持既有授权开启状态。

## 1. 当前基础与结论

- 可以配置多个企业微信收件人，但目前是全局股票/主题/关注点/推送等级；多个收件人收到同一套预警，不是独立订阅。
- `db.py` 的 `config_state` 是单例，stocks/themes没有成员归属；`callback_service.py` 只允许管理员修改全局配置。已有成员绑定的上下文、确认令牌和定向管理回执可复用，但不能据此认为订阅权限已隔离。
- `monitor.py` 当前按目标串行抓取、按文章串行分析，seen全局去重，文章ID直接作为outbox唯一事件。`delivery.py` 的新闻预警默认发送给全部 `WECOM_TOUSER`，不能直接用于不同成员订阅。
- `news.py` 目前只有东方财富搜索适配器，已有统一文章结构和可替换transport；多源接入需要真正的来源层，而不是简单增加几个URL。
- 三项功能都具有实施路径。建议保持自有Python业务服务，增加订阅与渠道适配层，不为每位成员复制部署或调度器。

## 2. 多成员独立订阅与共享处理

### 2.1 成员与权限

首版限定一个现有组织内的多成员，不直接扩展为多企业SaaS。成员以服务端核验的企业ID/UserID映射内部身份，不以微信昵称、手机号或消息正文里的用户ID作为授权依据；外部联系人不等同于组织成员，不能把external_userid直接当内部touser使用。

新增成员、角色、渠道绑定和个人订阅。每个人分别保存股票、行业、关注点、推送等级、暂停状态、生效时间及递增订阅版本；公共证券目录、来源配置和成员准入由管理员维护，普通成员只能查看、修改自己的订阅。现有全局配置迁移时明确原拥有者，不默认广播复制给所有新成员；新成员默认空订阅。

自然语言、确认、审计、异步任务和查询全部带成员作用域，不能只在微信入口做一次鉴权。组织成员加入/移除、应用可见范围、停用账号、解绑和取消订阅都要有生命周期处理；生成消息和实际发送前重新校验资格，撤销尚未发送的相关任务。

### 2.2 抓取一次，按需有限并行

每轮汇总所有有效订阅，按“来源、目标、规范化检索条件、时间窗口”取并集，相同检索任务只抓一次，不按成员重复抓。每个来源仍可能需要分页、多关键词或增量请求；“抓取一次”指共享查询结果，不是承诺全部来源只发一个HTTP请求。

沿用唯一worker和全局调度租约。在现有1核1GB机器上，建议抓取全局并发从2、每域名1开始，模型并发从1开始；数字只是待压测初值，还须服从上游更严格限频。设置请求/解析大小、超时、队列容量、组织总预算和每人公平额度；长扫描拆成可恢复的小任务，避免阻塞管理回执。网络请求期间不持有SQLite写事务，不增加每成员cron或Web调度器。

### 2.3 AI是否每人分别请求

**首选按“实际分析需求”分组复用，不按微信号机械拆分。**

| 差异 | 建议 |
| --- | --- |
| 同一文章、目标及关注点，只是收件人或推送等级不同 | 共享一次结构化分析，本地按各人等级等规则筛选，分别投递 |
| 同一文章，但关注的公司、问题或分析范围不同 | 按规范化“目标+关注配置”分组；不同组分别分析，同组成员复用 |
| 需要个人私有背景或独特判断 | 独立请求并隔离结果，不把多人的私有背景合进公共提示词 |

例如10位成员关注同一批10篇新闻，分析需求完全相同时，按人重复分析可能需100次请求，分组后可约为10次（不含重试）；关注组变多时调用量仍会增加，不能承诺固定成本。仅“基础分析一次再为每人补分析”的两阶段方案也可能更贵，作为后续按实测token、质量和时延决定的优化，不作为首版必选。

当前模型对一篇文章只返回一个总等级/方向，多订阅版需要文章—目标/关注组的受约束结果，避免A公司的重要利好被原样用于B公司。缓存键至少包含内容版本/哈希、分析目标、规范化关注配置、模型标识及可用版本、提示词版本、输出结构版本；不能只按文章ID，也不能因接收人或推送等级变化就重复分析。私有上下文加入成员隔离域；缓存不等于无期限有效，供应商模型变更和材料修订须失效。

### 2.4 去重、基线与投递必须拆层

- 共享文章已抓取/已分析，不代表每位成员都已评估或收到。全局内容存储与成员评估/通知状态分开，禁止A先写seen就吞掉B的通知。
- 按成员、渠道绑定和文章事件建立独立投递状态；普通订阅版本变化不能自动生成旧闻重发。相同文章命中同一成员多项订阅应合并或去重，一个成员投递失败不能重发其他已成功成员。
- 分析完成后在短事务内生成所有通知，或原子落地可恢复的fan-out工作清单；禁止先全局标完成，再不可恢复地逐个排队。保留现有分段检查点与重试，网络结果不确定仍可能重复，不承诺外部严格一次投递。
- 新增/恢复订阅按生效时间监控，默认不补历史；已有内容池也不能自动把旧闻补发给新成员。基线按成员订阅及来源/目标区分，显式补查才允许回溯。

## 3. 推送到个人微信的路线

### 3.1 优先验证：企业微信的微信插件

当前成员已于2026-10-22完成该路线的真实验收：个人微信收到授权文字测试，“查看监控”可返回本人订阅。后端继续使用现有企业微信应用、UserID和凭证，不把“微信客户端接收”等同于“完全移除企业微信后端”。具体操作及验收证据见[PERSONAL_WECHAT.md](PERSONAL_WECHAT.md)。[腾讯官方企业微信API说明](https://cloud.tencent.com/document/product/1301/88712)

该路线复用现有组织及后端；当前账号由实际关注、应用可见范围检查和手机收件确认验通，不依赖网页描述推断。其他账号是否可用仍取决于插件入口、成员绑定、应用可见范围和接收设置。企业微信帮助页读取受站点限制，新增账号沿下述路径独立检查，不自动推广本次结果。

**以下供后续成员经授权接入时使用；当前成员已完成，不要重复绑定或重复发送测试：**

| 页面 | 操作或填写 | 预期结果 |
| --- | --- | --- |
| 企业微信管理后台 → 通讯录 | 邀请指定测试成员并完成组织身份验证；核对内部UserID，不粘贴到聊天 | 成员有效且身份可映射 |
| 应用管理 → 股票新闻助手 → 可见范围 | 加入该测试成员 | 该成员有权使用应用；不因此授予全局配置管理权 |
| 我的企业 → 微信插件（若账号提供） | 查看邀请关注二维码和允许接收/回复相关设置，成员本人用个人微信扫码绑定 | 个人微信出现组织/应用入口；入口缺失则先记录账号限制，不放宽权限绕过 |
| 个人微信中的组织/应用会话 | 经明确投递授权后验收指定成员通知；再单独发送只读查询验证回调 | 实际收到且只发给本人；能回调并收到查询回执才标记双向可用 |

仅收件成功时保留企业微信会话或未来管理页作为配置入口。新增多个成员不会自动赋予他们当前 `WECOM_ADMIN_USERIDS` 的全局权限。若同一成员同时在两端显示同一应用消息，不为两个客户端再发送两次。

### 3.2 不依赖组织的个人微信渠道：独立可行性试验

现在不能笼统断言“微信没有官方机器人接入”：腾讯已公开 [OpenClaw Weixin Channel](https://github.com/Tencent/openclaw-weixin)，支持扫码及多账号；[腾讯云官方渠道说明](https://cloud.tencent.com/document/product/1759/132562)也列有微信ClawBot。它不是本项目已经支持的功能，也不是普通好友/微信群任意群发接口。

可将官方ClawBot/iLink列为候选渠道适配器，但须另行验证主动预警的会话上下文、长期不交互时是否可推送、条数/时限、凭证续期/撤销、多个绑定的隔离与部署资源。官方[协议说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md)明确区分客户端行为和服务端保证，不能因为context_token可选或某次发送成功，就认定长期无人值守推送可行；本次不采信第三方固定额度作为平台承诺。

现成插件依赖Node/OpenClaw，不能为接收通知便直接在1GB生产机装完整智能体栈；先隔离评估轻量适配可行性、官方允许范围与资源成本。业务继续Python3.12，任何桥接服务单独审查，不授予股票服务执行任意Shell/工具的能力，也不引入第二个新闻调度器。

若今后面向不加入组织的大量订阅者，再评估公众号/小程序账号和合适的消息能力。小程序订阅消息需要用户授权，普通一次性订阅不是授权一次就无限推送；不能假设金融资讯有可用长期模板。[腾讯官方订阅消息说明](https://cloud.tencent.com/document/product/1301/103770) 公众号的资质、模板/场景、频次、授权及分发规则届时单独核对，不把客服对话当永久主动预警通道。第三方转发平台会增加消息外流和依赖，仅在操作者接受后评估；不采用非官方个人号登录、Hook或绕过限制的机器人。

## 4. 更多信息源

建议优先补“原始公告与公司披露”，再增加授权财经/行业媒体，优先提高可信度而非单纯增加新闻数量。

现有东方财富来源也要在扩展多人使用前复核服务条款、摘要存储及多人分发范围，不能把目前技术上能请求成功当作用途已全部获准；本轮不改变其线上配置。

| 顺序 | 候选 | 接入前置条件 |
| --- | --- | --- |
| P1 | A股公告：上交所、深交所、巨潮/深证信正式数据服务 | 核对正式API或许可渠道、证券映射、时效、限频、费用，以及缓存、AI处理和多人分发权；公共查询页不等于免费开放API |
| P2 | 公司官网IR/新闻稿、明确提供的RSS/Atom | 逐站审核使用许可、机器读取入口和发布时间；不能假设每家公司都有RSS，也不能借官网嵌入页绕过上游限制 |
| P2可选 | SEC EDGAR官方API/RSS，补充阿里等美国披露 | 核对公司CIK、覆盖表单、fair access、时区与语言；仅补充，不代替港股或A股披露 |
| 授权后 | 港交所IIS或取得相应用途授权的数据供应商 | 披露易网站现行条款限制程序化访问、抓取及自动分析；不直接开发网页爬虫。IIS许可也须覆盖实际缓存、模型处理和下游分发用途 |
| P3 | 财经媒体与行业源 | 优先明确提供的RSS/API或授权服务；不绕过验证码、登录、付费墙，不默认免费、不直接转载全文 |

已确认候选入口：[上交所公告](https://www.sse.com.cn/disclosure/listedinfo/announcement/index.shtml)、[深交所公告](https://www.szse.cn/www/disclosure/listed/notice/index.html)、[深证信数据服务](https://webapi.cninfo.com.cn/)、[SEC官方数据](https://data.sec.gov/)。具体接口及用途许可未申请验收。港交所限制及授权路线依据：[披露易使用条款第5节](https://www2.hkexnews.hk/Global/Exchange/Terms-of-Use?sc_lang=zh-HK)、[HKEX IIS](https://www.hkex.com.hk/Services/Market-Data-Services/Infrastructure/Issuer-Information-feed-Service-%28IIS%29?sc_lang=en)。技术可行不替代用途授权，robots规则也不等于内容/模型/分发许可。

### 多源数据与可靠性要求

1. 来源登记保存许可范围、复核日期、限频、可用时段与启用状态；未确认许可/凭证的来源保持disabled。每源适配器统一返回文章、游标、分页完整性和成功/失败状态，不能把429/解析失败当作“查无新闻”。
2. 主键使用来源命名空间+上游ID，记录规范链接、证券/主题映射、发布时间/更新时间/抓取时间、语言、内容哈希、材料是摘要还是全文及来源证据。当前raw_id未分来源，需迁移兼容而非直接切换导致全量重发。
3. 精确去重优先公告编号/规范链接/内容哈希，再保守分组转载事件；不单凭相似标题合并。保留全部出处，修订、更正、撤销和实质新增材料有独立版本/事件，不被旧seen永久挡住。
4. 每个来源/目标独立游标与初次基线。接入新源先静默建立基线，不因为目标已有基线就批量推送新源旧闻；临时故障恢复不得再次建基线而吞掉故障期间新闻。限定分页和重叠时间窗口，明确延迟或数据不完整状态。
5. 每源独立超时、退避、熔断和限频，遵循Retry-After，支持ETag/Last-Modified（上游支持时）。一个源失败不阻断其他源，仍保留失败源重试与评估状态，不能将不完整文章判断为整体处理完成。
6. PDF仅在用途允许后限大小/页数/解析时限处理，初始单任务解析；不在1GB机器启用浏览器集群或本地模型。内容一律不可信；域名白名单、重定向校验和内网地址拦截防SSRF，禁止执行外部文本或模型指令。摘要和可获取全文区分，模型输出不得谎称读过完整公告。

## 5. 实施顺序与验收门槛

- **阶段5：当前成员微信插件接收与只读双向查询已验收。** 1条授权测试、个人微信实际收件、本人查询回执均已验证；其他成员/媒体类型须独立验收，ClawBot只保留为可选候选，不为本次接收另装智能体栈。
- **阶段6：多成员隔离和共享处理基础。** 先设计统一来源身份/内容版本，再做成员/订阅/分析缓存/通知分层，迁移保留当前拥有者配置；共享抓取、关注组分析、成员级队列、撤权、预算和公平调度。先本地离线实现，不改当前线上名单。
- **阶段7：逐源启用。** 在来源适配层上优先接入有权使用的公告与IR/官方数据；每源单独审核和验收。HKEX等所需授权或预算未明确时只暂停对应来源，其他离线适配测试继续。
- **后续优化：** 根据调用/token、缓存命中、分析质量、端到端延迟和资源峰值，再决定两阶段AI、更多并发、摘要合并或汇总推送。不在本规划内承诺付费额度、可支持人数或采购升级。

最低验收覆盖：A/B成员配置与自然语言隔离、同查询抓一次、同关注组只分析一次/异组不串缓存、A先处理不吞B、单成员失败不重发其他人、新订阅/新源基线、撤权后不发、fan-out中断与重启恢复、跨源ID冲突/转载/修订、源部分失败和限额、恶意正文/PDF/URL、单worker受控并发与管理回执时延。先全部离线模拟，再按逐项授权做最小真实联调；迁移前备份并兼容旧版本，自动回退仍服从数据库结构兼容边界。
